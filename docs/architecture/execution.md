## Durable queue storage and fenced leases (U13, partial)

Framework metadata migration 6 adds deployment-scoped jobs, unique deduplication keys, function/build payloads, verified identity snapshots, due times, retry limits, lease ownership/fencing, cancellation, results and fixed failure codes. `createJobQueue` is a trusted server primitive. `enqueue` validates a registered mutation/action and its arguments against the captured registry version, then inserts through the supplied database transaction. Mutation handlers must await it with `context.db` so domain changes, jobs and output validation share their transaction. This primitive is not a browser authorization boundary or the final generated scheduler API. Deployment identity scopes deduplication; the same key with different function, identity, arguments, due time or retry policy fails. The original UUID remains after success/failure, and claimed mutations carry that UUID as their idempotency key. Defaults permit one attempt; explicit policies allow up to ten attempts and a fixed retry delay of zero to 3,600 seconds. Arguments are limited to 64 KiB and saved results to 1 MiB.

Claims use PostgreSQL row locks with `SKIP LOCKED`, following its [queue-consumer locking guidance](https://www.postgresql.org/docs/18/sql-select.html). Complete/fail/renew reject expired or superseded leases. A contention regression initially showed that a clock predicate could run before a row-lock wait; a second materialized CTE now checks eligibility only after receiving the locked row. The test holds the lock until expiration and verifies that acknowledgement fails.

Cancellation prevents pending execution immediately. For a running job it records a request and refuses renewal; failure or lease expiry then records cancellation. A successful completion can still win because cancellation cannot undo already completed effects. Inspection retains terminal state/result/error, and failed jobs are not silently recreated under the same deduplication key.
