## Declare capabilities

Neon supplies extension binaries; PostgreSQL installs each extension into an individual database. Declare the capabilities your application needs in optional `loom.config.ts`.

```ts
import { defineConfig } from "loom/tooling";

export default defineConfig({
  database: {
    extensions: {
      vector: { version: "0.8.6" },
      pg_trgm: { version: "1.6", schema: "text_search" },
    },
  },
});
```

Names have completion from Loom's Neon PostgreSQL 18 catalogue, checked on October 1, 2026. The catalogue excludes entries blocked for new installation. Availability and privileges are checked against the target database. The public authoring types are `NeonExtensionName` and `LoomExtensionsInput` from `loom/tooling`.

Versions are exact PostgreSQL version tokens. Loom does not interpret semver ranges or select the latest version. Inspect the target with `loom migrations status`; when preparing a new pin, query `pg_available_extension_versions` through the migration-owner connection.

## Choose placement and dependencies

Omitted `schema` means `extensions`. A custom schema must be a lowercase PostgreSQL identifier, at most 63 characters, outside reserved `pg_`, `loom_` and `information_schema` names. Loom checks ownership and schema privileges before installation.

Some extensions require a fixed schema. Specify that schema explicitly when the default conflicts with the target's control metadata. A nonrelocatable extension without a fixed schema can permit initial placement while refusing a later move. Loom preserves provider-owned schemas and extension members; it does not rewrite their ownership or routine privileges.

Relocation also requires ownership of the affected members. Neon can assign trusted-extension routines to its administrative role even when the migration role owns the extension. Choose the intended schema at installation or request provider assistance when Loom reports missing member ownership.

Declare every required extension dependency explicitly with its own pin. For example, `earthdistance` requires `cube`; Loom orders their installation and never installs undeclared dependencies with `CASCADE`.

Qualify extension SQL when the schema is outside the runtime search path:

```sql
SELECT text_search.similarity('loom', 'loom framework');
SELECT '[1,2,3]'::extensions.vector;
```

## Use configured extensions in TypeScript

Generation reads `database.extensions` and gives the selected APIs to RPC handlers through `context.extensions`. Schema files import the same bindings from `./_generated/extensions`; Effect handlers obtain them through the generated `Extensions` service. With no declarations, or an empty extensions object, the binding is `undefined`.

Configuration declares what the database needs. `loom generate` creates TypeScript bindings; it does not install an extension. `loom dev` installs safe first-time declarations before table DDL. Existing installations, upgrades and moves follow the reviewed migration workflow below.

This example selects four reviewed adapter versions. Omitted placement still means `extensions`:

```ts title="typed/loom.config.ts"
import { defineConfig } from "loom/tooling";

export default defineConfig({
  project: "typeddocs",
  database: {
    namespace: "app",
    extensions: {
      pg_trgm: { version: "1.6", schema: "text_search" },
      citext: { version: "1.8" },
      pg_uuidv7: { version: "1.6" },
      pgcrypto: { version: "1.4" },
    },
  },
});
```

Use an extension's field and index helpers when it supplies a native type. `citext` preserves the stored spelling while PostgreSQL applies its case-insensitive comparison rules. Its array field preserves PostgreSQL dimensions and lower bounds; it is not a plain JavaScript array.

```ts title="typed/loom/schema.ts"
import { defineSchema, defineTable } from "loom/server";
import { extensions } from "./_generated/extensions";

export default defineSchema(
  (s) => ({
    tasks: defineTable(
      {
        title: s.text().notNull(),
        label: extensions.citext.field().notNull(),
        tags: extensions.citext.arrayField(),
      },
      {
        indexes: [{ fields: ["label"], extension: extensions.citext.indexes.btree() }],
      },
    ),
  }),
  { namespace: "app" },
);
```

Declare a contract for each handler. Extension expressions have fixed output types: similarity returns a nullable number, and a Pgcrypto digest returns checked binary data as `{ hex: string } | null`.

```ts title="typed/loom/contracts/tasks.ts"
import { defineContract, oc } from "loom/contract";
import * as v from "valibot";

const search = oc.input(v.strictObject({ query: v.string() })).output(
  v.array(
    v.strictObject({
      title: v.string(),
      score: v.nullable(v.number()),
      hash: v.nullable(v.strictObject({ hex: v.pipe(v.string(), v.regex(/^[0-9a-f]{64}$/)) })),
    }),
  ),
);

export default defineContract({ search, effectSearch: search });
```

Call the shallow helpers directly. They return typed SQL expressions that compose with the normal database API; execution happens when the query runs. The helpers qualify the configured schema and parameterize values.

```ts title="typed/loom/functions/tasks.ts"
import { Effect } from "effect";
import { asc, desc } from "drizzle-orm";
import { os } from "../_generated/rpc";
import { Database, Tables, Extensions } from "../_generated/server";

export default os.tasks.router({
  search: os.tasks.search.handler(async ({ context: { db, tables, extensions }, input }) => {
    const score = extensions.pg_trgm.similarity(tables.tasks.title, input.query);
    const hash = extensions.pgcrypto.digest(tables.tasks.title, "sha256", "text");
    return db
      .select({ title: tables.tasks.title, score, hash })
      .from(tables.tasks)
      .orderBy(desc(score), asc(tables.tasks._id))
      .limit(20);
  }),
  effectSearch: os.tasks.effectSearch.effect(function* ({ input }) {
    const db = yield* Database;
    const tables = yield* Tables;
    const extensions = yield* Extensions;
    const score = extensions.pg_trgm.similarity(tables.tasks.title, input.query);
    const hash = extensions.pgcrypto.digest(tables.tasks.title, "sha256", "text");
    return yield* Effect.tryPromise(async () =>
      db
        .select({ title: tables.tasks.title, score, hash })
        .from(tables.tasks)
        .orderBy(desc(score), asc(tables.tasks._id))
        .limit(20),
    );
  }),
});
```

Configure your application's authorization policy before exposing these procedures. Extension bindings carry SQL capabilities, not permission to read a table or administer the database. Administrative and session-changing operations stay outside RPC bindings.

The digest's `"text"` argument selects the PostgreSQL text overload; `"bytea"` selects checked binary input. Both return a fixed checked binary type, decoded as lowercase hex.

Pgcrypto PGP helpers use the same database query API. This Effect example receives its passphrase from the application and returns checked ciphertext:

```ts title="typed/loom/pgp-example.ts"
import { Effect } from "effect";
import { Database, Tables, Extensions } from "./_generated/server";

export const encryptTitles = (passphrase: string) =>
  Effect.gen(function* () {
    const db = yield* Database;
    const tables = yield* Tables;
    const extensions = yield* Extensions;
    const ciphertext = extensions.pgcrypto.pgpSymEncrypt(tables.tasks.title, passphrase);
    return yield* Effect.tryPromise(async () => db.select({ ciphertext }).from(tables.tasks).limit(20));
  });
```

Checked PGP encryption and decryption require PostgreSQL 18.6 or later within PostgreSQL 18 (`180006 <= server_version_num < 190000`). Loom checks the executing backend before the PGP statement runs. Execute these expressions through Loom's database API so that check and the binary decoder run. Raw `PgDialect` compilation is refused. The application supplies key management and authorization; SQL crypto operations do not grant Loom invocation identity.

## Available typed adapters

The current generated API selects these exact reviewed versions:

| Extension       | Version | Examples of direct helpers                                |
| --------------- | ------- | --------------------------------------------------------- |
| `pg_trgm`       | `1.6`   | `similarity`, similarity operators, trigram index classes |
| `fuzzystrmatch` | `1.2`   | Edit distance and phonetic matching                       |
| `pg_tiktoken`   | `0.0.1` | Token counts with `bigint` results                        |
| `pg_jsonschema` | `0.3.4` | JSON Schema validation with distinct JSON/JSONB inputs    |
| `uuid-ossp`     | `1.1`   | `v4`, `v5`, namespace helpers                             |
| `citext`        | `1.8`   | `equal`, case-preserving fields, arrays and index classes |
| `pg_uuidv7`     | `1.6`   | `v7`, timestamp conversion and extraction                 |
| `pgcrypto`      | `1.4`   | `digest`, `hmac`, checked binary crypto and PGP helpers   |

Configuration of another extension or version yields a descriptor with `name`, `version`, `schema` and `apiSupport`, without invented query methods. Check `apiSupport.status` and, for an unverified descriptor, `apiSupport.reason`. Installation support and typed adapter support are separate: a captured SQL catalogue alone does not establish a reviewed executable API. Full Neon catalogue coverage remains in progress; vector, GIS and the other pending families do not yet have generated typed helpers.

Pgcrypto 1.4 exposes all 37 captured SQL routine signatures through its reviewed adapter. This does not mark the whole family or Neon catalogue as accepted. Algorithm and option availability follows the target's native crypto implementation; true process-FIPS mode and unproved provider profiles remain pending. `fipsMode()` observes process state, while the `pgcrypto.builtin_crypto_enabled` setting controls a separate native policy. Random and session-dependent helpers do not support automatic live subscriptions.

Prefer the direct helper names for ordinary queries. Each adapter also exposes its exact captured SQL names under `sql.functions`, `sql.operators` and `sql.casts` where applicable; casts cover actual PostgreSQL cast edges, and overloads keep their native argument types. These are fixed contracts rather than caller-selected output generics.

Native values that cannot fit a JavaScript primitive use checked constructors from the public adapter modules. For example, `loom/extensions/pg-jsonschema` exports `jsonValue` and `jsonbValue`; use `jsonDocument` or `jsonbDocument` when exact numeric text must survive. `loom/extensions/timestamps` exports `timestamp` and `timestamptz` for distinct civil and instant values, with native microseconds, extended years and infinities preserved. Native Drizzle timestamp columns use the corresponding `timestampColumn` or `timestamptzColumn` bridge.

UUID generation uses database randomness. UUIDv7 timestamp extraction also exposes time encoded in the identifier. Random and session-dependent expressions cannot serve as observable prepared/live query expressions. In `pg_uuidv7` conversions, only a literal `true` zero flag selects deterministic output; omitted, false or dynamic flags retain native randomness. Exact temporal decoding requires PostgreSQL's ISO DateStyle and refuses ambiguous output.

## Develop and release

Safe first installations run before dependent application and component DDL during `loom dev`. Repeated sync verifies the same state and does no work. Existing unmanaged installations, version changes and schema moves require a reviewed migration.

```sh
loom migrations generate --name add_extensions
loom migrations status
loom migrations apply --runtime-role application_runtime
```

Generation needs the dedicated migration connection to inspect available binaries and supported update paths. Commit configuration and migration artifacts together. Supply `--reviewed-hash <artifact-hash>` for adoption, upgrades and supported moves. An extension-only change is retained in history even when table snapshots are unchanged.

Application operations and dependent SQL share a transaction. Components carry requirements without repeating the database-wide installation. Removing a declaration retains the installation; Loom does not generate `DROP EXTENSION` or reverse updates on code rollback.

Upgrades and moves require retained runtimes to retire and their jobs and unexpired sessions to drain. Structural schema ranges are insufficient evidence for changed extension behavior. This implementation requires retirement; it does not accept a self-declared compatibility flag.

Runtime roles receive usage of owned extension schemas, without CREATE or extension administration authority. Ordinary application tables that use extension types remain managed by Loom. Extension members and their subordinate objects are excluded from application snapshots and blanket grants.

## Branches and deployment

Project provisioning verifies source capabilities under the database-wide migration lock. Parent-data branches verify copied state without repeating installation. Schema-only branches accept matching copied capabilities and install only missing committed requirements before adopting migration history. Portable observations use names rather than object IDs.

Retain the branch's `.loom/provision` receipts with the project. Loom records the guarded creation and verifies provider creation, reset and restore metadata before connecting to a clone. Existing external clones without that proof, and branches reset or restored after creation, require a fresh guarded branch. Inspecting the parent now cannot establish which schedules an older clone inherited. Connection helpers accept an optional `root` for locating receipts when called outside the project directory.

In Neon acceptance testing, a schema-only clone installed `pg_trgm` at the provider's default `1.6` when its source used `1.3`. Loom refused that mismatch. Check the installed version when cloning older pins; use a reviewed source upgrade or a branch mode that preserves the required state before accepting the baseline.

Release receipts include extension requirements and committed operations. Live version or placement drift blocks release preparation, activation and resume, including a retry of completed stages. Preserve the original declaration and receipts when diagnosing a failed deployment.

## Provider prerequisites

| Extension or condition             | Required action                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pg_cron`                          | Use the configured cron database and an endpoint whose verified suspension timeout is `-1`. Neon requires active compute for scheduled execution.             |
| Inherited active cron jobs         | Disable schedules before cloning. Loom holds the source job-table guard through provisioning and refuses unsafe external clones before waking target compute. |
| TimescaleDB background workers     | Loom currently refuses cloning because it cannot verify prevention before target compute starts.                                                              |
| `pg_repack`                        | Resolve paid-plan, Support enablement and restart prerequisites with Neon. Loom does not request enablement or restart compute.                               |
| Fixed-schema or privilege conflict | Choose the permitted schema or correct migration-owner privileges, then regenerate/review the migration.                                                      |

Loom reports unavailable versions, missing dependencies, invalid update paths, placement conflicts, privileges and provider prerequisites separately. Automatic restarts, provider settings changes and background-worker reconfiguration are outside this integration.

## Acceptance evidence

On October 1, 2026, Neon PostgreSQL 18 acceptance passed with `vector` at `0.8.6` and a reviewed `pg_trgm` upgrade from `1.3` to `1.6`. Both parent-data and schema-only branches passed baseline verification, database activation, authenticated runtime SQL and denial of runtime extension DDL.

The required cloud fixture runs with `LOOM_CLOUD_SUITE=extensions bun run test:cloud`, disposable `LOOM_CLOUD_PROJECT_ID` / `LOOM_CLOUD_BRANCH_ID` values and `LOOM_CLOUD_PROVISION_ROOT` pointing to the project with the branch's creation receipts. It checks actual PostgreSQL 18 installations, custom placement, extension-only releases, database activation, resumed drift refusal and both branch modes. The receipt records tested versions and cleanup. Local PostgreSQL tests cover PostgreSQL contrib extensions, dependency ordering, membership, grants and transaction failures.
