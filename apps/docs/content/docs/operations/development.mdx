title: Development

## Select a development target

Run `loom login` and link an unprotected, nondefault PostgreSQL 18 branch with `loom link --project-id <id> --branch <branch-id>`. Normal linked projects need no `loom.config.ts`: Loom discovers the database owner and prepares its restricted runtime login. Explicit configurations must keep development separate from their preview and production targets.

Optional operational overrides belong in `loom.config.ts`:

```ts
development: {
  databaseName: "neondb",
  migrationRole: "neondb_owner",
  runtimeRole: "loom_runtime",
},
```

The official Neon login supplies provider access; CI can use `NEON_API_KEY`. Loom resolves runtime credentials through Neon and stores its development activation secret in owner-only Postgres metadata, keeping it stable across generations and restarts. Custom credential-source names and preexisting unmanaged roles require explicit overrides. Application secrets remain separate from these framework-owned credentials.

An explicit `--development <file>` declaration remains available for advanced orchestration, but normal development needs no extra script or declaration file.

## Watch and serve

Run `loom dev --cwd <project>`. The watcher generates a candidate, checks safe schema synchronization and verified runtime startup, then publishes its API and listener together.

Invalid source, unsafe changes or failed startup preserve the prior serving generation. If no generation has started, the watcher remains alive so a corrected edit can recover. Additive DDL already committed before a startup failure remains in the database. Declaration or credential changes require a restart.

Old requests drain through their generation, and old sockets close so clients can reconnect. SIGINT and SIGTERM stop admission and drain owned work. Use [release migrations](/operations/migrations) for changes that development synchronization refuses.

## Jobs, crons and storage

Published generations poll durable jobs; the default interval is 1000 milliseconds. Local crons evaluate UTC schedules without replaying missed minutes. Replacement stops old background loops before starting the new generation's loops.

Storage-enabled projects also need the branch's private buckets and credentials configured through the project settings. Startup verifies bucket metadata and target binding. It does not provision those resources or emulate provider-attested object events.

## Quarantine copied work

Stop development before running `loom dev quarantine --cwd <project>`. This revokes active Loom grants and cancels pending/running jobs in the selected development metadata namespace, including locally created work. It preserves application data and completed jobs.

Quarantine is database-only. Stop relevant workers and disable unwanted provider triggers separately; it cannot undo external effects already performed. Restarting development establishes its own branch-bound activation grant.
