## Schedule internal work

Declare a handler with `internalMutation` or `internalAction` and generate its internal reference. Inside a mutation, call `ctx.scheduler.runAfter(delayMs, reference, args, policy)` or `ctx.scheduler.runAt(dateOrEpochMs, reference, args, policy)` and await the returned job ID.

Use the generated reference rather than constructing a name or contract version by hand. Queries are not job targets. A mutation's scheduled jobs commit with its application writes; rollback removes both. A due time is a not-before bound, not an exact execution time.

## Choose retry behavior

The optional policy accepts `deduplicationKey`, `maxAttempts`, and `retryDelaySeconds`. Defaults are one attempt and a one-second retry delay. Attempts are bounded at 10 and retry delay at 3600 seconds. Supply a stable deduplication key when repeated scheduling represents the same logical work; otherwise scheduling creates a fresh key.

Workers claim leased jobs and use fencing tokens to reject stale owners. Database mutations retain their transaction guarantees. External action effects cannot be rolled back: use `ctx.job.id`, which stays stable across attempts, as the external service's idempotency key where supported. Observe cancellation through the context signal.

Do not use a database completion record as proof that an external service delivered an email or completed a payment. Record and inspect the external service's result separately.

## Declare recurring work

Default-export an object of named `cron(expression, internalReference, args, policy)` declarations from `loom/crons.ts`. Schedules use five numeric fields in UTC, with lists, ranges and steps. Names, macros and a seconds field are not accepted.

In local development, the published generation evaluates schedules from the next minute boundary. It does not replay the startup minute or missed minutes after sleep or downtime. Failed dispatch can retry while that minute remains current; enqueued jobs then follow their stored retry policy. Cloud schedules arrive through verified provider trigger ingress and durable occurrence deduplication.

## Deploying with queued jobs

Jobs retain their function contract version. Keep compatible workers available while pending or running jobs depend on them. Release migration checks include these dependencies; deleting an old worker merely because new code is deployed can strand work. [Deployment](/operations/deployment) explains release and retirement boundaries.
