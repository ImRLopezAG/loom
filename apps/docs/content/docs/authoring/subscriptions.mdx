## Configure one authenticated session

The generated factory binds native oRPC clients and TanStack options to one QueryClient and identity. Keep the session stable across renders.

```tsx
import { createRpcTransport } from "@loom/core/client";
import { QueryClientProvider } from "@tanstack/react-query";
import { createApi, version } from "../loom/_generated/api";

const transport = createRpcTransport({ url, version, getToken });
const session = createApi({
  link: transport.link,
  deployment: url,
  version,
  identity: { issuer, subject },
});
const { api, queryClient } = session;

<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>;
```

`getToken` must return credentials only for this session's identity. Before switching user or tenant, call both `session.dispose()` and `transport.dispose()`, then create a new session and remount its subtree. Disposal aborts pending calls and clears observer data and caches. Do not share a QueryClient across identities or server-rendered requests. Tokens never belong in query keys.

## Query and mutate

Generated methods return native TanStack options directly. `input` contains procedure input; other properties retain upstream option types and override defaults.

```tsx
import { useQuery, useMutation } from "@tanstack/react-query";

const tasks = useQuery(
  api.tasks.list({
    input: { projectId },
    enabled: !!projectId,
    select: (rows) => rows.filter((row) => !row.done),
  }),
);

const setDone = useMutation(api.tasks.setDone({ onSuccess: (task) => console.log(task) }));
setDone.mutate({ id: taskId, done: true });
```

Inputs, return values, selectors and callbacks infer from native procedures. TanStack owns cache, observers, retries and React state. Loom does not add an entity store or a second hook system.

Custom `queryKey` and `mutationKey` replace the inner native key while retaining the deployment, version, identity and mode partition. Options cannot replace `queryFn` or `mutationFn`; use `.native` for upstream utilities or `.call` for a direct native call when you need that control. Options reject execution through another session's QueryClient.

## Live results and finite snapshots

Server `clientMode` metadata chooses finite query, live query, or mutation options. A live procedure returns a native async iterator; oRPC's `liveOptions` feeds TanStack. Matching observers share the cached stream. Each authorized reevaluation sends a complete result snapshot. The last observer's removal cancels that stream.

Live fetching stays open. Use `isPending` for initial loading; `isFetching` is not a connection-health indicator. Native TanStack policies still apply: changing `refetchOnMount` or choosing static stale time can prevent resubscription.

For prefetching, SSR or Suspense, use a finite snapshot:

```ts
await queryClient.fetchQuery(api.tasks.list.snapshot({ input: { projectId } }));
```

`.snapshot` consumes the first result and closes the iterator. It uses the configured link; it does not imply HTTP. Finite and live keys differ. A browser live query can start with its hydrated finite value and then attach a stream. Use the native serializer when dehydrating values such as Date or bigint. Dispose each SSR session after its request.

## Optimistic updates

Mutations default to `retry: false`. Connection recovery never automatically repeats an uncertain write. Opting into retries requires an application-level decision about idempotency and external effects. Callable mutation options preserve one idempotency key across that mutation's retries, including option updates; the next mutation gets a new key. For explicit raw calls through `createRpcTransport`, pass the same UUID as `context.idempotencyKey` only when retrying the same logical write. External providers must honor that key themselves.

`optimisticMutation(session, affectedKeys, options)` wraps native mutation options. It pauses the selected live keys before `onMutate`, cancels in-flight evaluations and resumes after the last overlapping mutation settles. Supply cache edits and rollback through TanStack callbacks. The helper cannot infer how to merge overlapping optimistic edits or undo an external side effect.

```ts
import { optimisticMutation } from "@loom/core/query";

const mutation = optimisticMutation(
  session,
  () => [api.tasks.list({ input: { projectId } }).queryKey],
  api.tasks.setDone({ onMutate, onError, onSettled }),
);
```

If a callback throws after a successful write, `OptimisticCallbackError.committed` is true. Do not roll back a confirmed server write merely because a success callback failed. Session disposal prevents late callbacks from repopulating the old identity's cache.

## Change detection

In notification mode, committed database revisions wake one restricted direct PostgreSQL listener per active runtime. Revisions remain durable truth; reconnect reconciliation covers missed notifications. A coordinator bounds reevaluation concurrency and keeps one unread snapshot per subscription. Polling mode uses the configured interval and has different freshness characteristics.

Notifications do not carry user data or replace authorization. Every reevaluation executes the procedure's authorization and database-read transaction. See [operating limits](/operations/limits) for measured acceptance and resource bounds.
