## Query and mutate

Generated public methods return native TanStack Query options. Query arguments live in `input`; other properties use TanStack's normal option types and override Loom's defaults.

```tsx
import { useQuery, useMutation } from "@tanstack/react-query";
import { api } from "../backend/_generated/api";

const tasks = useQuery(
  api.tasks.list({
    input: { projectId },
    enabled: !!projectId,
    select: (rows) => rows.filter((row) => !row.done),
  }),
);

const setDone = useMutation(
  api.tasks.setDone({
    onSuccess: (task) => console.log(task),
  }),
);
setDone.mutate({ id: taskId, done: true });
```

Read `tasks.data`, `tasks.error`, and the standard `pending`, `success`, or `error` status. Inputs, wire-encoded results, selectors, mutation variables, and callbacks infer from the backend schema. Loom reexports the unchanged TanStack hooks from `@loom/core/react` for convenience. Actions also produce mutation options and run with `useMutation`.

`queryKey`, `queryFn`, `mutationKey`, and `mutationFn` belong to the generated method. Other native options, including `enabled`, `select`, `initialData`, `placeholderData`, `meta`, retry settings, and mutation lifecycle callbacks pass through. Keys include the contract version, function name, canonical input, and live/finite mode. The tagged key works with `queryClient.getQueryData(options.queryKey)` and cache invalidation.

## Configure a session once

```tsx
import { createClient, createLiveQueryClient } from "@loom/core/client";
import { createLoomQueryClient, LoomProvider } from "@loom/core/react";

const client = createClient({ url, getAuth });
const live = createLiveQueryClient({
  url,
  client,
  deployment,
  identityKey,
});
const queryClient = createLoomQueryClient({ client, live });

<LoomProvider client={client} live={live} queryClient={queryClient}>
  <App />
</LoomProvider>;
```

Create these instances outside rendering and keep them stable for that session. `createLoomQueryClient` accepts native `QueryClient` configuration, including cache instances and default options. Components need no client utility factory. A standard `QueryClientProvider` also works when given this configured client; `LoomProvider` additionally supports `useLoomClient` for imperative calls and storage.

Each QueryClient belongs to one deployment and identity. When the user or tenant changes, synchronously call `live.setIdentity(nextIdentity)` before rendering the replacement session. This cancels work, clears query and mutation caches, and retires the old QueryClient. Create a fresh QueryClient for the replacement identity and remount the session subtree. On sign-out pass `null`; on application disposal call `live.stop()` and `queryClient.dispose()`. Keep the HTTP token supplier aligned with the identity partition, which must distinguish issuer, subject, and tenant. Never share a QueryClient between server requests.

## Live and finite queries

Queries are live by default. Loom authenticates the WebSocket, shares matching subscriptions, reconnects, and provides complete result snapshots. TanStack owns the cache, selection, observers, and hook state. One stream serves matching observers; the last observer's removal releases it. Returning to a cached live query resubscribes by default. Overriding `refetchOnMount` or using `staleTime: 'static'` can prevent that subscription, as with any TanStack fetch policy.

Live results use TanStack's pinned `experimental_streamedQuery` with a latest-snapshot reducer. A live query becomes successful after its first snapshot and remains fetching while listening. Use `isPending` for initial loading; `isFetching` is not a connection-health signal. The last successful value remains visible during a reconnect. Identity changes clear it.

A live fetch stays open. For imperative fetching, prefetching, server rendering with Suspense, and `useSuspenseQuery`, use finite HTTP mode:

```ts
const options = api.tasks.list({ input: { projectId }, live: false });
await queryClient.fetchQuery(options);
```

Finite and live modes have separate cache keys. A normal server render with `useQuery` stays pending without opening connections; hydration and prefetching should use finite mode and a request-scoped QueryClient. Do not await a live fetch or use it with Suspense: its promise lasts for the subscription's lifetime.

## Mutations and optimistic updates

Mutation options default to no TanStack retries. Loom's HTTP transport retains its bounded retries and reuses a mutation idempotency key. If you opt into TanStack mutation retries, Loom retains the same key for that one execution; a later `mutate` gets a new key. Actions are not idempotent, so enabling action retries explicitly permits repeated side effects. Persisting and replaying pending mutations across page reloads is not supported by this adapter.

Use native `onMutate`, `onError`, `onSuccess`, and `onSettled` with the QueryClient for application-specific optimistic changes. Loom does not install an optimistic entity store. A successful mutation does not certify that every live query has observed its commit; an older server snapshot can still arrive before reevaluation. Automatic optimistic confirmation needs a future server revision contract.

## Bounds and freshness

The live client defaults to 32 active subscriptions; `maxSubscriptions` accepts 1 through 1000. Only subscribed stores occupy capacity. The server checks table revisions and reevaluates affected subscriptions; its default polling interval remains one second. This adapter does not change server detection latency. See [operating limits](/operations/limits).
