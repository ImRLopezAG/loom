## Connect through a provider

For normal React applications, follow [React clients](/clients/react). The Loom provider manages token changes, connection disposal, and identity-scoped cache namespaces. [Suspense](/clients/suspense) and [SSR](/clients/ssr) are separate choices.

## Advanced: manage a connection yourself

Loom generates the authenticated oRPC client factory. TanStack owns the cache and React hooks. Keep these objects stable for one signed-in identity.

```tsx
import { createTanstackQueryUtils } from "@orpc/tanstack-query";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { createClient } from "../loom/_generated/api";

const connection = createClient({ url, getToken });
const rpc = createTanstackQueryUtils(connection.client);
const queryClient = new QueryClient();

<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>;
```

`getToken` must return credentials only for this connection's identity. When switching users or tenants, unmount the old subtree, clear its QueryClient and dispose its connection. Create fresh instances for the new identity. Do not share a QueryClient across identities or server-rendered requests. Tokens never belong in query keys.

```ts
queryClient.clear();
connection.dispose();
```

## Use native options

The following examples assume your application declares `users.user` and `users.update` contracts. See [procedures](/authoring/functions) for contract and handler definitions.

```tsx
import { useQuery, useMutation } from "@tanstack/react-query";

const user = useQuery(
  rpc.users.user.queryOptions({
    input: { id },
    enabled: !!id,
    select: (user) => user.name,
  }),
);

const update = useMutation(rpc.users.update.mutationOptions({ onSuccess: (user) => console.log(user) }));
update.mutate({ id, name: "Ada" });
```

These are oRPC's own utilities. Inputs, outputs, selectors and callbacks retain their native types. Caller options override native defaults, including custom keys and functions where upstream allows them. Loom uses native options and the TanStack cache. Its provider assigns an identity-scoped cache namespace. If you manage connections manually, you must also manage their cache lifetime; application-specific invalidation remains your responsibility.

## Declare subscriptions explicitly

A streaming contract uses `eventIterator`. Zod and Valibot both work through Standard Schema; this declaration uses Valibot.

```ts
// loom/contracts/tasks.ts
import { defineContract, oc, eventIterator } from "loom/contract";
import * as v from "valibot";

export default defineContract({
  titles: oc.output(eventIterator(v.array(v.string()))),
});
```

```ts
// loom/functions/tasks.ts
import { os } from "../_generated/rpc";

export default os.tasks.router({
  titles: os.tasks.titles.handler(({ context }) =>
    context.live(async ({ db, identity }) => {
      if (!identity) throw new Error("Authentication required");
      const rows = await db.query.tasks.findMany({
        columns: { title: true },
        where: { ownerId: identity.subject, ownerIssuer: identity.issuer },
        orderBy: { _createdAt: "asc", _id: "asc" },
        limit: 100,
      });
      return rows.map((row) => row.title);
    }),
  ),
});
```

Apply the application's ownership filters to its reads. `context.live` reruns the handler and middleware for each authorized snapshot, then runs the callback with fresh database context. Streaming handlers and middleware must be safe to reevaluate. A read-only SQL transaction does not make emails or other external effects repeatable.

```tsx
const titles = useQuery(rpc.tasks.titles.liveOptions({ enabled: true }));
```

Loom does not synthesize a `.live` route or convert finite outputs into streams. Native contracts validate every event. Matching observers share a cached stream; removing the last observer cancels it. Use `isPending` for initial loading. A live query can remain fetching while receiving updates, so `isFetching` is not a connection-health indicator.

## Optimistic updates and retries

The cache-edit example uses the contracts in `packages/examples/tasks`: `list` accepts `projectId`, and `setDone` accepts `id` and `done`.

Use TanStack's native mutation callbacks or render pending mutation variables over the latest server data. For a cache edit, cancel the affected query before changing it, retain rollback data, and invalidate after settlement. Overlapping writes require application-specific reconciliation; a whole-cache rollback can overwrite another write.

```ts
const live = rpc.tasks.list.liveOptions({ input: { projectId } });
const options = rpc.tasks.setDone.mutationOptions({
  onMutate: async (input) => {
    await queryClient.cancelQueries({ queryKey: live.queryKey });
    const previous = queryClient.getQueryData(live.queryKey);
    queryClient.setQueryData(live.queryKey, (rows) =>
      rows?.map((row) => (row._id === input.id ? { ...row, done: input.done } : row)),
    );
    return { previous };
  },
  onError: (_error, _input, rollback) => {
    if (rollback) queryClient.setQueryData(live.queryKey, rollback.previous);
  },
  onSettled: () => {
    // A live query stays active until cancellation; do not await its completion.
    void queryClient.invalidateQueries({ queryKey: live.queryKey });
  },
});
```

Mutations do not retry by default. Connection recovery does not replay an uncertain write. If you explicitly retry a logical write, reuse a UUID in `context.idempotencyKey` for those attempts only; generate a new UUID for the next logical write. Native mutation options do not create a durable intent identifier for you. External providers need their own idempotency guarantees. Cache callbacks remain application code: guard them against identity changes and distinguish callback failures from failed server writes.

## Change detection

Committed database revisions wake a restricted PostgreSQL listener in notification mode. Revisions remain durable truth; reconnect reconciliation covers missed notifications. The coordinator bounds reevaluation concurrency and keeps one unread snapshot per subscription. Polling mode uses the configured interval.

Notifications do not contain user data or replace authorization. Every reevaluation reruns authorization in a fresh read-only transaction. See [operating limits](/operations/limits) for acceptance evidence and resource bounds.
