## Build the local package

Use the repository's pinned Bun toolchain and Node 24 for the framework examples. Loom uses TypeScript 7, Vite+, Oxlint, and Turborepo. From the repository root:

```sh
bun install --frozen-lockfile
bunx turbo run build --filter=loom
```

The examples consume the built `loom` package through public subpath imports such as `loom/server` and `loom/react/neon`. Version `0.0.0` is a workspace evaluation target; these instructions do not assume an npm release exists.

## Choose an example

| Directory                        | Client behavior                                                                    |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `packages/examples/next`         | `/client`: client-only live query; `/`: optional bearer-authenticated SSR          |
| `packages/examples/start`        | `/client`: client-only Suspense live query; `/`: optional bearer-authenticated SSR |
| `packages/examples/tasks`        | React/Vite tasks and optimistic updates                                            |
| `packages/examples/jobs-storage` | Private uploads and durable processing                                             |
| `packages/examples/components`   | Mounted component APIs and services                                                |

Each example owns its backend. Link separate disposable branches so their schemas and deployment identities do not conflict.

## Authenticate and link

From the selected example directory:

```sh
bunx --no-install loom login
bunx --no-install loom link --project-id YOUR_PROJECT_ID --branch YOUR_BRANCH_ID
bunx --no-install loom doctor --json
```

Loom uses the official Neon credential profile and discovers the database and migration owner. Choose an unprotected, nondefault development branch. CI can use `NEON_API_KEY`; do not put provider credentials in browser variables. A normal linked project does not need `loom.config.ts`. Examples may retain namespace overrides.

Copy the example's `.env.example` to `.env` and configure its application values. Managed Neon auth also requires branch auth setup and the correct allowed frontend origin. Backend auth secrets belong on the Loom service, never in a `NEXT_PUBLIC_*` or `VITE_*` variable.

## Generate and review the database

```sh
bun run generate
bunx --no-install loom schema diff
bunx --no-install loom migrations generate --name initial
bunx --no-install loom migrations status
```

If the example already has a migration history, retain it and inspect the diff instead of creating a second initial migration. Commit reviewed history under `loom/_generated/migrations`. Generation alone does not apply SQL or deploy functions.

## Deploy and connect

```sh
bunx --no-install loom deploy --dry-run --json
bun run deploy
```

The linked deployment flow prepares the restricted runtime role, applies eligible migrations, deploys the service and worker, and activates the verified runtime. Changes requiring review must be explicitly approved by migration hash; do not bypass a rejected migration.

For Next.js set `NEXT_PUBLIC_LOOM_SERVICE_URL`; for Start set `VITE_LOOM_SERVICE_URL`. Use the deployed service URL before building:

```sh
bun run build
bun run start
```

Open `/client` to see browser-owned authentication and live data without a server loader or hydration. Open `/` for the optional SSR path. Backend and frontend processes are separate: `loom dev` watches the backend; each framework's frontend dev server serves its UI.

Managed Neon hosted browser login still has a recorded multi-`Set-Cookie` delivery acceptance issue. Local fixture success does not establish hosted session persistence. See [authentication](/authoring/auth) and [limits](/operations/limits) before treating a deployment as accepted.

## Create or integrate your own project

Use `loom init <directory> --name <name>` to scaffold source locally, or `loom integrate` to preview additions to an existing frontend and `loom integrate --apply` to write them. These commands do not silently overwrite existing files. Install/link the local Loom package while no public release is available. Use `loom create <directory> --name <name> --region <region>` only when you intend to create provider resources.

Read [project configuration](/authoring/configuration) for the file layout and [CLI commands](/reference/cli) for operational options.

## Run the docs

```sh
bun run --cwd apps/docs dev
```

The documentation and its source examples build without Neon credentials. Cloud acceptance and local database integration tests require their own explicit targets.

## Check that setup worked

| Check                                  | Expected result                               | If it fails                                                 |
| -------------------------------------- | --------------------------------------------- | ----------------------------------------------------------- |
| `loom doctor --json`                   | The intended project loads with its contracts | Check the working directory, link, and configuration        |
| `loom generate`                        | New methods appear in `_generated/api`        | Match contract files to default-exported routers            |
| `loom deploy --dry-run --json`         | A reviewable plan for the intended branch     | Check credentials, drift, and migration review requirements |
| Authenticated browser call             | Private data belongs to the signed-in user    | Check token trust and server authorization                  |
| A write while a second view subscribes | The subscribed view receives a new snapshot   | Check worker/runtime logs and live-query configuration      |

For a local Next or Start frontend, run `bun run dev:backend` in one terminal and `bun run dev` in another from that example directory. Set the frontend's public Loom URL to the backend address printed by `loom dev`, then restart the frontend. Vite examples use their own `dev:frontend` script; inspect the selected example's `package.json` instead of assuming all scripts match.

If Astro says another docs server is running, open its printed URL. To replace it deliberately, run `bunx astro dev --force` from `apps/docs`; to stop it, run `bunx astro dev stop` there. This affects the documentation server, not Loom's backend watcher.
