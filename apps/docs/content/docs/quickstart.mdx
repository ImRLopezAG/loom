## Prepare the workspace

Use the repository's pinned Bun toolchain. From the repository root:

```sh
bun install --frozen-lockfile
bun run build
bun run check
```

The workspace uses TypeScript 7, Vite+, Oxlint, and Turborepo. TypeScript source imports use extensionless relative paths, such as `import { schema } from "./schema"`.

The packages are currently private. These instructions apply to a checkout of the repository; a public package installation is not available yet.

## Run the tasks application

The projects/tasks example includes a React interface, committed migrations and live queries backed by PostgreSQL 18. Start a local database:

```sh
docker run --name loom-tasks-postgres -e POSTGRES_PASSWORD=local-example-only -p 127.0.0.1:54329:5432 -d postgres:18
```

Then run the example from the repository root:

```sh
LOOM_LOCAL_DATABASE_URL=postgresql://postgres:local-example-only@127.0.0.1:54329/postgres bun run --cwd packages/examples/tasks dev
```

Open `http://127.0.0.1:5173` and continue as Alice. Create a project and add a task. Open a second window as Alice to see live changes, or choose Bob to see a separate workspace.

The launcher prints its temporary database name. You can inspect that database using the PostgreSQL connection above. Ctrl-C removes the example's database and runtime role. Restart after changing source. The two demonstration identities and ephemeral signing key are local-only; production requires a trusted identity provider. The launcher refuses remote database addresses.

This checkout example does not yet prove installation from release artifacts or a Neon deployment. Those acceptance checks are separate from local application behavior.

## Try uploads and durable processing

After the workspace build, start the upload catalog with the same local PostgreSQL 18 administrator connection:

```sh
LOOM_LOCAL_DATABASE_URL=postgresql://postgres:password@127.0.0.1:5432/postgres \
  bun run --cwd packages/examples/jobs-storage dev
```

Stop the tasks app first if it is using port 5173. Choose a local user and upload a file. Normal processing creates a catalog record from verified metadata. The two demonstration modes intentionally retry once or fail all three attempts. The original verified bytes remain available through a private download.

This app uses a temporary PostgreSQL database and an in-memory HTTP object store. Ctrl-C removes both. It summarizes media type, size and fingerprint, rather than analyzing file contents. Its backend has an independent configuration and committed migration. It is local acceptance, not proof of a Neon deployment.

## Understand the backend

A Loom backend declares tables and relations, exports validated queries, mutations and actions, and generates a client contract. Queries read data. Mutations write inside a transaction. Actions perform external work outside a database transaction.

Start with [schemas](/authoring/schemas). Deployments also need migration credentials, a restricted runtime role, authentication configuration, and a reviewed migration history.

Use this project layout:

```text
loom.config.ts
backend/
  schema.ts
  relations.ts
  auth.ts
  functions/
    tasks.ts
  _generated/
migrations/
```

The schema, relations and auth modules use default exports; function modules use named registered exports. The generated directory is owned by tooling. Match the schema's namespace to the configured database namespace (`app` by default). The authoring examples use this layout and compile against a packed public API.

After defining [functions](/authoring/functions) and [authorization](/authoring/auth), connect [React subscriptions](/authoring/subscriptions). Follow [development](/operations/development) for a guarded development target and [migrations](/operations/migrations) before changing a shared database. [Jobs](/authoring/jobs) and [storage](/authoring/storage) describe durable background work and private uploads.

## Inspect the documentation locally

```sh
bun run --cwd apps/docs dev
```

The documentation builds without Neon credentials. Database integration tests and cloud acceptance use separate, explicit targets. Read the [limits](/operations/limits) before running those tests.
