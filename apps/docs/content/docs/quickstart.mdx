## Prepare the workspace

Use the repository's pinned Bun toolchain. From the repository root:

```sh
bun install --frozen-lockfile
bun run build
bun run check
```

The workspace uses TypeScript 7, Vite+, Oxlint, and Turborepo. TypeScript source imports use extensionless relative paths, such as `import { schema } from "./schema"`.

The packages are currently private. These instructions apply to a checkout of the repository; a public package installation is not available yet.

## Run the tasks application

The projects/tasks example uses Neon PostgreSQL, Neon Functions and Neon Auth. Choose a development or preview branch in your Neon project, enable Neon Auth, and allow your frontend origin.

From `packages/examples/tasks`:

```sh
cp .env.example .env
# Fill the branch ID, database credentials and Neon Auth URL.
bun run generate
bunx loom migrations apply --runtime-role loom_runtime
bun run deploy
# Set VITE_LOOM_URL to the service invocation URL returned by deployment.
bun run dev:frontend
```

`loom.config.ts` names the connection environment variables and declares the development and deployment settings. Keep migration credentials separate from the restricted runtime login. The migration command creates the runtime role; provision its login credentials through Neon before deploying. Set `LOOM_ACTIVATION_TOKEN` to a stable random 64-character hexadecimal secret.

Sign up through Neon Auth, create a project and add a task. Open another signed-in window to see live updates. `bun run dev` starts the Loom development server against the configured Neon development branch.

## Try uploads and durable processing

Configure `packages/examples/jobs-storage` using its `.env.example` and the same generation, migration and deployment commands. Deploy to a separate example branch. Loom provisions the declared private buckets and binds the worker triggers during deployment.

File bytes live in **Neon Object Storage**. PostgreSQL stores ownership, verified metadata and durable processing jobs. The browser uploads through a signed URL; Loom verifies and seals the object before making it available through authorized signed downloads. Provider object-created events wake processing. The example supports successful processing, a retry followed by success, and terminal failure.

Local database, fake-session and object-store implementations are isolated regression fixtures under `packages/e2e/fixtures`. They are not part of the application setup.

## Understand the backend

A Loom backend declares tables and relations, exports native oRPC procedures, and generates a typed client. Database middleware grants read or write transactions. Bare procedures perform work without database authority. Client presentation metadata chooses finite, live or mutation options.

Start with [schemas](/authoring/schemas). Deployments also need migration credentials, a restricted runtime role, authentication configuration, and a reviewed migration history.

Use this project layout:

```text
loom.config.ts
loom/
  schema.ts
  relations.ts
  auth.ts
  functions/
    tasks.ts
  internal/
    maintenance.ts
  _generated/
  migrations/
```

The schema, relations and auth modules use default exports; procedure modules use named procedure exports or explicit routers. The generated directory is owned by tooling. Match the schema's namespace to the configured database namespace (`app` by default). The authoring examples use this layout and compile against the built public API.

After defining [functions](/authoring/functions) and [authorization](/authoring/auth), connect [React subscriptions](/authoring/subscriptions). Follow [development](/operations/development) for a guarded development target and [migrations](/operations/migrations) before changing a shared database. [Jobs](/authoring/jobs) and [storage](/authoring/storage) describe durable background work and private uploads.

## Inspect the documentation locally

```sh
bun run --cwd apps/docs dev
```

The documentation builds without Neon credentials. Database integration tests and cloud acceptance use separate, explicit targets. Read the [limits](/operations/limits) before running those tests.

## Generated files and migrations

Author functions under `loom/functions`. `loom generate` maintains stable imports under `loom/_generated`, including project-bound procedure bindings in `server.ts`. Immutable runtime builds are disposable cache under `.loom/generations`; activation retains the current build and one predecessor. Commit migrations under `loom/migrations`, separately from generated imports, because deployed databases need their complete history.

`loom dev` and `loom deploy` read their settings from `loom.config.ts`. Connection configuration names environment variables; credentials belong in `.env` or the deployment environment. See the tasks and upload-catalog example READMEs for Neon setup.
